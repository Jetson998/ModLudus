# ModLudus 产品体验重构方案 V1

状态：产品方向已确认，P0 前端重构进行中。

产品定位：基于真实业务任务的多模型竞技、自动评审与智能选型平台。

核心闭环：外部市场基线帮助发现模型 → 真实任务发起评测 → 多模型作答 → 自动评审与人工复核 → 质量/成本/速度/稳定性比较 → 选型建议 → 可追溯报告 → 实测数据叠加到模型天梯。

## 1. 当前单页体验的核心问题

本结论基于当前 `page.tsx`、`batch-lab.tsx`、`trusted-season.tsx` 和本地实页，不只是基于规划文档。

1. **入口与任务混在一起**：首页同时承担营销首页、快速对比表单、批量评测工作台、标准评测控制台、榜单和产品说明，首屏之后没有稳定导航或当前位置。
2. **用户目标不清楚**：普通用户不能快速判断“快速对比、批量评测、标准评测”分别解决什么问题，也不知道应该选哪一种。
3. **配置过早暴露**：用户还没有明确任务，就会看到 Base URL、Key、Model ID、OpenRouter 价格和裁判网关等大量工程字段。
4. **流程没有阶段感**：快速对比和批量评测都把输入、连接、评审、运行和结果堆在同一页面，没有步骤、完成条件或返回路径。
5. **结果层级倒置**：候选原文和技术指标先出现，真正的“该选哪个模型”在更下方。用户需要自行拼接质量、成本和速度结论。
6. **三种可信度混淆**：本地个人结果、社区授权指标和平台固定标准评测没有成为三个清晰的数据来源；演示榜单容易被误解成真实结果。
7. **技术术语面向错误人群**：`Trusted Season`、`Manifest`、`Ed25519`、`Worker`、`append-only` 等信息应进入验证详情或运维文档，不应成为普通用户的主标题。
8. **版本号替代产品语言**：`M3.1 / M3.3` 是研发里程碑，不是用户任务。主界面应使用“可恢复”“固定规则”“已验证”等用户能理解的状态。
9. **批量结果缺少专业视图**：已有批量执行和导出能力，但缺少模型×题目矩阵、筛选、两次运行差异和分类汇总等高频分析入口。
10. **首页榜单缺少来源证据**：静态演示排名没有报告入口、样本范围、评测版本和更新时间，不符合 ModLudus 的“有证据来源”定位。
11. **响应式只是压缩布局**：390px 不溢出已实现，但复杂表单和大量卡片仍需要更适合手机的分步、折叠和底部主操作。
12. **缺少主题与国际化基础**：当前中文字符串散落在组件中，无法可靠切换英文；主题、语言和术语没有统一令牌层。

## 2. 用户类型与目标

| 用户类型 | 主要目标 | 最短成功路径 | 默认模式 |
|---|---|---|---|
| 第一次比较模型的个人用户 | 用一道真实任务快速判断哪个模型更适合 | 选示例 → 添加模型来源 → 开始 → 看推荐 | 快速对比 |
| 产品经理 / AI 应用团队 | 用真实测试集做选型、回归和报告 | 导入测试集 → 设置评分 → 批量运行 → 看矩阵与建议 | 批量评测 |
| 评测负责人 / 人工复核者 | 处理低置信度、失败和高价值样本 | 打开复核队列 → 查看逐题证据 → 提交决定 | 批量评测 / 标准评测 |
| 采购、技术负责人和研究用户 | 对比模型质量、价格、速度与适用场景 | 筛选天梯 → 查看模型 → 追溯报告 | 模型天梯 |
| 平台管理员 | 执行固定规则评测并发布可验证结果 | 启动评测任务 → 复核 → 验证 → 发布榜单 | 标准评测 |

产品不为每类用户做一套独立系统，而是通过模式入口和逐级展开控制复杂度。

## 3. 新的信息架构

### 一级导航

1. **首页 / Home**
2. **模型评测 / Model Evaluation**
3. **模型天梯 / Model Ladder**

“模型评测”内部包含单次对比、批量评测和我的评测。“标准评测”是模型天梯的可信数据生产方式，不再占一级菜单；普通用户从标准评测榜查看报告，管理员从受保护入口进入执行控制台。“评测资料库”改为辅助入口“评测指南”，未来真正接入可运行数据集时，在模型评测流程内增加“测试集库”。

右侧固定工具：评测指南、隐私状态、语言切换、主题切换。管理员和复核令牌只在标准评测控制台临时输入，不进入全局账户状态。

### 推荐路由

```text
/
├── /evaluations
│   ├── /quick/new
│   ├── /quick/run                     # 当前标签页内存结果
│   ├── /batch/new
│   ├── /batch/run                     # 当前标签页内存与脱敏恢复点
│   └── /mine
├── /ladder
│   ├── ?view=overall|copy|code|summary|analysis
│   ├── /models/[model-id]
│   └── /standard-reports/[run-id]
├── /guides
│   └── /guides/[dataset]
└── /admin/standard-evaluations        # 受保护的低频管理入口
```

快速对比与批量评测使用浏览器内存中的统一 `EvaluationSession`。客户端路由切换可以保留会话；刷新后快速对比敏感信息全部清空，批量评测只恢复既有脱敏检查点。

## 4. 关键用户动线

### 4.1 快速对比

```mermaid
flowchart LR
  A["选择任务或示例"] --> B["添加模型来源"]
  B --> C["选择 2-6 个候选模型"]
  C --> D["选择独立评审模型"]
  D --> E["确认调用范围与参考成本"]
  E --> F["运行与取消"]
  F --> G["先看选型结论"]
  G --> H["展开模型对比与逐题证据"]
```

向导收敛为三步：任务 → 模型与评审 → 确认并运行。高级参数默认折叠。连接模型服务时先显示业务标签“添加模型来源”，在辅助说明中再解释 OpenAI-compatible、Base URL 和 Model ID。

### 4.2 批量评测

```mermaid
flowchart LR
  A["新建评测"] --> B["平台示例或导入测试集"]
  B --> C["选择模型与评分标准"]
  C --> D["确认题目数、调用数和成本"]
  D --> E["批量运行"]
  E --> F["失败重试与自动抽检"]
  F --> G["摘要 / 矩阵 / 逐题"]
  G --> H["人工复核与报告导出"]
  H --> I["与另一评测任务比较"]
```

### 4.3 标准评测与榜单发布

```mermaid
flowchart LR
  A["查看评测版本与规则"] --> B["管理员启动评测任务"]
  B --> C["固定配置执行"]
  C --> D["验证报告"]
  D --> E["必要样本人工复核"]
  E --> F{"是否满足发布条件"}
  F -- 否 --> G["保持未发布并说明原因"]
  F -- 是 --> H["发布到标准评测榜"]
  H --> I["榜单反向链接具体报告"]
```

### 4.4 从榜单反查证据

模型天梯 → 选择数据来源 → 筛选场景/价格/速度 → 打开模型详情 → 查看贡献该结论的评测版本与报告 → 查看验证状态和逐类表现。

## 7. 移动端适配方案

1. 顶部导航收纳为抽屉，只保留品牌、当前页面、语言和主题入口。
2. 快速对比保持单列分步向导，底部固定一个主按钮；返回上一步保留非敏感输入。
3. 模型来源默认折叠为“名称 + 连接状态 + 已选数量”，展开后才显示 Base URL、Key 和模型发现。
4. 运行状态以纵向模型卡展示，不使用横向表格；状态、延迟、成本和失败原因分两层显示。
5. 结果页先展示推荐卡，再展示三个策略卡；指标表改为每个模型一张可折叠卡。
6. 批量矩阵在手机端切换为“按题目”或“按模型”列表，不缩放大型二维表格。
7. 标准评测的验证信息使用底部抽屉；哈希和公钥提供复制按钮并允许自然换行。
8. 图表在窄屏只保留一个主要维度，其他维度通过下拉切换，避免一次展示五条轴。
9. 触控目标至少 44px，正文不小于 14px，关键数字不依赖颜色表达状态。
10. 390px 验收继续要求横向溢出为 0，同时新增 320px 和 768px 两个布局检查点。

## 8. Light / Dark 设计系统

### 设计方向

可信、克制、偏现代数据产品。保留当前页面干净、留白充足的优点，减少橙色研发标签和超大标题对工作区的干扰。蓝色负责主要交互，绿色/琥珀/红色只表达状态。

| Token | Light | Dark | 用途 |
|---|---|---|---|
| `bg.canvas` | `#F6F8FB` | `#0E1117` | 页面背景 |
| `bg.surface` | `#FFFFFF` | `#151A23` | 卡片、侧栏、弹层 |
| `bg.subtle` | `#EEF3F8` | `#1C2330` | 次级区块 |
| `text.primary` | `#0F172A` | `#F1F5F9` | 标题、关键数字 |
| `text.secondary` | `#475569` | `#A8B3C5` | 正文、说明 |
| `border.default` | `#D8E0EA` | `#2A3442` | 边框、分隔线 |
| `action.primary` | `#174D3D` | `#7CC9A8` | 品牌、主按钮、推荐结论 |
| `action.data` | `#2563EB` | `#60A5FA` | 可点击数据、选中状态、图表 |
| `status.success` | `#15803D` | `#4ADE80` | 成功、已验证 |
| `status.warning` | `#B45309` | `#FBBF24` | 低置信度、待复核 |
| `status.danger` | `#B91C1C` | `#F87171` | 失败、阻断 |

基础规范：8px 间距体系；卡片圆角 12px，弹层 16px；正文使用系统字体栈，数字与 Model ID 可使用等宽字体；阴影只用于悬浮层，不用大面积渐变或霓虹效果。

主题偏好允许保存到 Local Storage。主题存储不得与评测会话、Key、Base URL、题目或答案共用数据结构。

## 10. 模型天梯的数据分层与评测指南边界

### 天梯必须先有初始化基线

模型天梯不能等待 ModLudus 积累足够评测后才有内容。首版应建立覆盖主流模型的市场基线，再把 ModLudus 的单次、批量、社区授权和标准评测聚合到相同模型实体上。

| 数据层 | 建议来源 | 提供什么 | 前台标识 |
|---|---|---|---|
| 模型目录与价格 | OpenRouter Models 等允许使用的公开接口 | Model ID、厂商、上下文、输入/输出价格、能力标签 | OpenRouter · 抓取时间 |
| 横向选型基线 | Artificial Analysis 的许可数据/API或经过授权的快照 | Intelligence、每任务成本、输出速度、TTFT、总响应时间 | Artificial Analysis · 指标定义 · 更新时间 |
| 市场与任务热度 | OpenRouter Rankings 的许可数据/API | 周使用量、任务分类、市场份额、语言、编程、工具调用、图像等导航 | OpenRouter Rankings · 时间范围 |
| 我的评测 | 浏览器当前会话 | 用户自己的任务结果，不上传 | 本地数据 |
| 社区实测 | 用户明确授权的最小化匿名指标 | 业务分类分数、胜负、成本/延迟区间、失败率 | 社区实测 · 样本量 |
| 标准评测 | 平台固定规则与正式非模拟运行 | 可验证业务质量、分类表现、稳定性、报告与复核状态 | ModLudus 标准评测 · 版本 |

外部数据接入必须保存 `source`、`source_url`、`captured_at`、`metric_definition`、`license_status` 和原始模型标识。没有明确许可或稳定接口时，产品可以展示来源链接和方法说明，但不能把抓取结果当作 ModLudus 自有数据长期复制发布。

### 一个天梯表格，三组指标

默认表格按模型展示，不把不同来源拆成互相隔离的空榜：

1. **市场基线**：外部质量指标、价格、输出速度、TTFT、上下文、市场热度。
2. **ModLudus 实测**：真实业务综合分、文案/代码/总结/分析分类分、胜率、失败率、实际成本与延迟。
3. **证据覆盖**：样本数、最近评测时间、数据来源、标准评测版本、验证与人工复核状态。

模型尚无 ModLudus 实测时仍可依靠初始化数据被发现，但实测列显示“待实测”，并提供“用此模型开始评测”。当实测数据增加时，只更新 ModLudus 指标列和推荐置信度，不覆盖外部原始指标。

### 不直接制造一个不透明总分

Artificial Analysis 的 Intelligence、OpenRouter 的使用/消费份额和 ModLudus 的真实业务质量不是同一个量，不能直接平均。天梯允许按质量、成本、速度、延迟、热度和业务分类分别排序；“智能推荐”必须展示权重、缺失数据处理和采用的数据来源。

推荐优先级：有同场景标准评测时优先使用标准评测；否则使用足量社区实测；仍无实测时使用外部市场基线，并明确标记“尚无 ModLudus 真实任务证据”。

### 任务分类与导航

参考 OpenRouter 的任务导航，但使用 ModLudus 的产品语言：综合、文案、代码、总结、数据分析、低成本、高速度、低延迟、中文、长上下文、工具调用。任务榜必须说明它按质量、使用热度还是成本排序。

### 模型统一身份

新增统一模型实体，解决不同来源名称不一致：

```text
CanonicalModel
├── canonical_id
├── provider / family / variant / reasoning_effort
├── aliases.openrouter[]
├── aliases.artificial_analysis[]
├── aliases.gateway[]
├── external_metric_snapshots[]
└── modludus_evaluation_aggregates[]
```

`GPT-X high`、`GPT-X max` 等推理档位不得错误合并；无法可靠映射的模型保持独立并进入人工映射队列。

### 评测指南

首批资料卡：MMLU、MMLU-Pro、GPQA、GSM8K、MATH、HumanEval、MBPP、IFEval、TruthfulQA、LongBench、C-Eval、CMMLU、MT-Bench、安全与合规评测、自定义业务测试集。

每张卡展示：能力标签、简介、语言、规模、评分方式、License、适合场景、局限性、官方文档、ModLudus 接入状态。未接入的数据集只提供资料，不显示可用按钮。它是辅助知识入口，不与“标准评测”并列成为核心菜单。

固定提示：**学术测试集得分高，不等于真实业务效果好。模型选型应同时考虑真实业务任务、成本、速度、失败率和人工复核。**

## 12. 第一阶段优先实现页面

第一阶段目标不是一次做完所有页面，而是先建立新的产品骨架，同时不损失现有可用能力。

### P0：产品壳层与快速对比闭环

1. 新建 App Shell、一级导航、响应式侧栏/抽屉。
2. 新首页：价值说明、场景入口、三种模式、隐私说明；移除首页大表单和伪榜单。
3. 快速对比分步向导：复用现有连接、模型发现、候选去重、评审和价格逻辑。
4. 快速对比运行/结果页：把“推荐模型和原因”前置，再展示模型比较和逐题证据。
5. 建立中英文消息层与 Light/Dark token；先覆盖新壳层和快速对比，不允许新增硬编码文案。
6. 将 `Trusted Season` 全部用户可见术语改为“标准评测”，底层 API 路径可暂时保持兼容。
7. 建立最小模型目录与外部指标快照结构，让首页天梯摘要和模型天梯从第一版就有带来源的初始化数据；不得继续使用无来源演示排名。

### P1：迁移专业工作区

1. 把现有批量评测完整迁移到独立页面。
2. 增加摘要、模型×题目矩阵、逐题模式和复核队列切换。
3. 增加两次评测任务 Diff 的数据结构和基础视图。
4. 把标准评测控制台迁移到独立列表/详情页，技术验证信息进入抽屉。

### P2：模型天梯与评测指南

1. 建立统一模型身份、外部指标快照和来源追踪结构。
2. OpenRouter 模型目录/价格由服务端共享快照接入；Artificial Analysis 先使用带来源、抓取时间和许可状态的公开页面参考快照，正式商业再发布前继续确认许可/API路径。两个来源都允许客户手动触发，但全站每个来源 24 小时最多成功更新一次。
3. 天梯同时展示市场基线、ModLudus 实测和证据覆盖，禁止把不同指标直接平均为不透明总分。
4. 建立可追溯的模型详情、来源方法和标准评测报告链接。
5. 上线评测指南第一批资料卡；“使用此测试集”只对真正接入的数据集开放。

### 第一阶段验收门槛

- 快速对比原有调用、评审、价格、隐私和失败隔离能力全部保留。
- 快速对比从首页进入到结果不超过五个明确步骤。
- 首页不出现 Base URL、Key、Rubric、Manifest 或 Worker 等配置。
- 所有用户可见 `Trusted Season/可信赛季` 改为标准评测术语。
- 中英文和 Light/Dark 可切换；只持久化语言和主题偏好。
- 刷新后 Key、Base URL、快速任务与答案仍清空；批量脱敏恢复规则不变。
- 390px、320px 和 768px 无横向溢出，主流程不依赖横向表格。
- 现有 Web/API 自动化测试继续通过，并补充路由、语言、主题和隐私状态测试。

## 建议确认的产品决策

本方案建议直接确认以下四点后进入代码重构：

1. 一级导航收敛为“首页、模型评测、模型天梯”，评测指南作为辅助入口。
2. 模型评测包含单次对比、批量评测和我的评测。
3. “可信赛季”在所有用户界面统一改为“标准评测”，并作为模型天梯的可信数据生产方式。
4. 模型天梯先用合规的 Artificial Analysis / OpenRouter 市场基线初始化，再叠加 ModLudus 实测；所有指标显示来源和更新时间。
5. 第一阶段先完成 App Shell、首页和模型评测闭环，再迁移标准评测控制台与模型天梯。
